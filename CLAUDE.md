# CLAUDE.md

## Product
A **standalone** youth sports scheduling tool for volunteer league schedulers (typically ~40 teams across several divisions, working at night after work). Load teams and facility time, set rules, generate a fair schedule in minutes, fix problems with a click, publish to families. The two guiding words are **easy** and **customizable**: smart defaults on the main path, optional depth behind "advanced" or per-division settings. Plain language everywhere. Never use solver jargon in the UI.

Primary user: the league scheduler. Then coaches, parents/players, and later referee assignors.

Plan and decisions: `docs/ROADMAP.md`. Engine design: `docs/ENGINE.md`. Phase 0 audit of the original prototype: `docs/AUDIT.md`.

## Run the whole app
```sh
cd web && npm ci && npm run build            # builds web/dist, which the API serves
cd ../api && uv sync && uv run uvicorn scheduling_api.server:app --port 8000   # http://localhost:8000
# while working on the UI: `cd web && npm run dev` (proxies /api to :8000)
cd ../web && node e2e/flow.mjs http://localhost:8000   # end-to-end check (needs Playwright + Chromium)
```
In the cloud sandbox Playwright is global: `PLAYWRIGHT_GLOBAL=$(npm root -g) node e2e/flow.mjs`. To stop the server use `kill` on the uvicorn PID; `pkill -f uvicorn...` also matches your own shell.

## Engine: run and test
```sh
cd engine
uv sync
uv run pytest -q
uv run ruff check src tests && uv run ruff format --check src tests && uv run mypy src tests   # mypy is strict
uv run pytest -q -m "not slow"   # skip the ~1-minute 40-team solves while iterating
uv run python -m scheduling_engine.fixtures ../fixtures   # after changing fixtures.py
uv run python -m scheduling_engine.bench --save --label "what changed"   # after any solver/goal change
```
CI (`.github/workflows/engine.yml`) runs lint, format, mypy and the full test suite (including slow tests).

## Engine conventions
- **`validate(league, events)` is the single source of truth for hard constraints.** The solver must produce zero violations on every fixture, and the UI's drag-and-drop checks will call the same function. Don't reimplement rule checks elsewhere.
- Every hard constraint (H1–H7 in `validate.py`) has tests that show a violation is caught *and* that the nearest legal case is not flagged.
- Messages are for volunteers: team, venue and coach names, never ids; full sentences. `test_messages_are_plain_language` enforces this.
- Surface sizing uses capacity **units** (full rink = 2, half-ice game = 1). Overlap is checked over time per surface, not per slot.
- Rules resolve league → division → team (`LeagueIndex.team_rules`). Overrides only set what they change.
- Setup problems (bad references, overlapping slots, tiny divisions) come from `check_setup`. It's forgiving: it returns problems and never raises.
- Fixtures are deterministic (seeded). `test_snapshot_matches_generator` fails if the JSON is stale.

## Solver conventions (`solver.py`, `goals.py`, `greedy.py`, `explain.py`, `regen.py`)
- Every solver output must pass `validate` with zero violations. Tests assert properties (legal, all placed), never exact schedules, because CP-SAT is multi-threaded.
- Fitting games always beats fairness: phase 1 places, phase 2 polishes with the placed count locked. Never merge them into one weighted objective.
- New fairness goals go in `goals.py` with a plain-language label in `GOAL_LABELS`, a unit cost in `UNIT`, and a matching measure in `report.py`. Then run the bench and save a labelled row.
- Explanations and suggestions must be verified, never guessed: suggestion counts come from an actual re-solve.
- `league_40` must stay fully schedulable. The "impossible league" scenario (no Sunday 75-min ice) is the test case for explanations.
## Importer conventions (`scheduling_engine/importer/`)
- Always two steps: `preview_teams / preview_coaches / preview_slots(league, data, filename)` returns an `ImportPreview` (summary, column matches, per-row problems); `apply_import(league, preview)` returns a **new** League. Nothing changes until apply.
- Never raise on bad input. Every problem is a `Problem` with the spreadsheet row number and a level: `skipped` (row left out), `check` (imported, worth a look) or `note` (FYI).
- Never silently merge a near-miss name ("U13s" vs "U13", "Nrth Arena"). Create it and flag it with "Did you mean…".
- Coach names are de-duplicated by `values.key()` across rows and files; that's how shared coaches are found.
- New messy real-world cases go in `engine/tests/data/` with a test.

## API and web conventions
- The API is thin: no scheduling rules in `api/` or `web/`. Drag-and-drop checks call `POST /api/seasons/{id}/check`, which uses `validate`.
- Every user action that changes a season goes through `Store.commit` with a plain-language action ("Moved Falcons vs Rovers…"). That string is what undo shows ("Undid: …").
- UI copy follows `design-system/README.md`: sentence case, no emoji, second person, no jargon ("constraint", "solver", "weight" never appear).
- Hide depth, don't remove it: advanced rule fields and partial regeneration sit behind a checkbox.

## Running the prototype
```sh
python3 -m http.server 8000   # from the repo root; open http://localhost:8000/prototype/Scheduling%20Workspace.dc.html
```
It needs unpkg.com reachable. In the cloud sandbox unpkg is blocked; get React with `npm pack react@18.3.1 react-dom@18.3.1 @babel/standalone@7.29.0` and serve it through Playwright `page.route`. Chromium is at `/opt/pw-browsers`. Don't run `playwright install`.

## Working conventions
- Plan before coding anything bigger than a small fix, and wait for approval.
- Work in small, testable increments. Commit after each working step. Work on a branch, never directly on `main`.
- Run all fixtures on every engine change.
- Don't silently rewrite working code. Explain why a refactor is needed and what it unlocks.
- When a requirement conflicts with how the app is built, flag it and recommend a path.
- Keep this file updated as the stack lands.
